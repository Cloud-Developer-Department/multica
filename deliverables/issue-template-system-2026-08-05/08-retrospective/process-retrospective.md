小队的 Coding 角色只有库里 1 人，后端（CLO-161）与前端（CLO-164）两个阶段只能串行执行，前端依赖后端 API 契约先定型，整体开发耗时明显拉长。

```

```

**根因**

**背景**

各角色通过 `multica repo checkout` 拉取代码时，该命令每次自动新建独立分支（命名 `agent/<角色>/<hash>`），没有约定共享特性分支。最终产生 11 个 agent 分支（6 个有提交、5 个空基线），Patrick 在 Stage 7 中要求统一到单条特性分支。

**时间线**

```

08-04 08:18  Patrick：不是说只用一条特性分支开发吗？现在多少分支了？
08-04 08:20  盘点 11 分支，确认提交单链（2e8d2102 → b71851b9）无分叉

08-05 01:37  姚明收拢完成：PR #2 已合并，删 6 个远端散落分支
```

**根因**

`multica repo checkout` 每次自动新建独立分支，未在拆解/执行约定中指定共享特性分支，导致分支随执行次数增长。

**修复动作**

- DevOps（姚明）把单链提交归并到 `Equipment_Department_Exploration`，提交统一 PR #2（90 文件，+4020/-65，rebase merge）。
- 删除 6 个远端散落分支（`agent/sgd-*`、`validation-issue-template`），删除前校验均为特性分支祖先或空基线，无内容丢失。
- 保留 `feature/issue-template` 作为统一 PR 来源分支，收口后删除。

**验证结果**

- PR #2 已 MERGED（rebase merge，提交 `4eb883fb`），代码全部在 `Equipment_Department_Exploration`。
- 远端散落分支已清理，确认无内容丢失。

**经验教训**

- 拆解时必须约定「共享特性分支」，并明确所有角色的 checkout 都基于该分支，禁止各自开新分支。
- `multica repo checkout` 的自动分支行为是分支散落的根源，使用前要明确目标分支策略。
- 幸运的是提交是单链无分叉，收拢成本低；若各分支并行修改同一文件，收拢代价会指数级上升。

## 4. 功能 Bug（部署后用户实测）

### 问题 6：issue 展示不全 + 无法使用模板创建

**背景**

本地部署完成后，Patrick 实测报两个症状：Settings → Templates 页签不显示模板（issue 展示不全），创建对话框的模板下拉不可用（无法用模板创建）。

**时间线**

```
08-04 07:33  Patrick 质疑缺部署任务，CLO-169 部署随之创建
08-04 08:42  ⚠️ Patrick 实测报 Bug：issue 展示不全 + 无法用模板创建
08-04 08:43  建 CLO-172 Bug 修复（Stage 8）
08-04 17:43  修复提交 4eb883fb（label_ids null → []，前后端契约对齐）
08-05 02:22  CLO-169 本地部署 done
08-05 02:23  CLO-172 done
```

> 说明：Bug 为用户在部署/运行环境实测反馈（08-04 08:42），CLO-172 于同日创建并修复，最终在 CLO-169 部署闭环中复验通过。

**根因**

（CLO-172 定位）前后端联调不完整：

- 后端 `parseLabelIDsJSONB` 对空 label 数组返回 `nil`，序列化为 JSON `null`。
- 前端 zod schema `z.array(z.string()).optional().default([])` 只对 `undefined` 生效默认值，对 `null` 直接拒绝。
- 整个 `ListIssueTemplates` 响应因 `label_ids: null` 校验失败，前端回退为空列表 → 模板页签空白、模板下拉不渲染。

**修复动作**

- 后端：空数组返回 `[]string{}`，`label_ids` 序列化为 `[]` 而非 `null`。
- 前端：schema 改为 `.nullish().transform(v => v ?? [])`，对旧服务端响应做防御性解析。
- 补入验证：Coding 产出根因报告 + 验证报告，经 PR #3 补入仓库。

**验证结果**

修复后 4 个预置模板正常列出，创建对话框模板下拉正常渲染，端到端验证通过（CLO-172 done）。

**经验教训**

- 前后端类型契约要对齐「空值」语义：`null` vs `[]` vs 缺省，一方认为是空数组、另一方拒绝 `null`，是典型的联调断裂点。
- 单元/集成测试要覆盖「空 label」这种边界输入，不能只测 happy path。
- 部署后应主动做一轮用户视角冒烟，而不是等用户实测报错。

### 问题 7：模板正文在新建 issue 时未带出

**背景**

功能整体可用后，Patrick 实测发现：从模板创建 Issue 时，标题能带出，但正文（body_template）不会填充到新建 issue 的描述编辑器。

**时间线**

```
08-05 01:40  Patrick：新问题——模板正文在新建 issue 时不会被添加进去
08-05 01:41  建 CLO-187 Bug 修复（Stage 10）
08-05 02:19  CLO-192 复审通过（PR #4）
08-05 02:43  CLO-191 复部署验证通过
08-05 10:25  PR #4 合并（rebase merge，提交 6d400f2d）
```

**根因**

`applyTemplate` 选择模板正文后调用 `setFormResetKey` 以重挂载正文编辑器，但只有标题编辑器（`TitleEditor`）挂了 `key={formResetKey}`，正文编辑器（`ContentEditor`）没有 key。`ContentEditor` 将 `defaultValue` 视为「仅挂载时读取」，不重挂载就无法读取新的 `body_template`，因此模板正文永远无法显示到编辑器中。

**修复动作**

- `packages/views/modals/create-issue.tsx:882`：为 `ContentEditor` 补上 `key={formResetKey}`，与 `TitleEditor` 一致，模板正文在重挂载后以 `defaultValue` 形式带出。
- 新增回归测试「pre-fills the title and body when a template is applied」，提交的 create-issue 请求断言含 `description`（模板正文）。

**验证结果**

- 回归测试修复前失败、修复后通过；create-issue 套件 37 个用例全过，typecheck 通过。
- 复部署（CLO-191）：线上服务加载的前端 chunk 与本地构建产物 SHA 一致，端到端 API 验证 4 个预置模板 `body_template` 正常下发，「从模板创建」对话框可带出正文。

**经验教训**

- React 编辑器组件用 `defaultValue` 存初始内容时，「重挂载」是唯一可靠的刷新手段；所有依赖重挂载的表单字段必须统一挂 `key`，不能只挂一部分。
- Bug 修复要有回归测试锁定，防止同类问题（标题带了、正文没带）复发。
- 修复必须落到构建产物验证（SHA 一致），避免「代码改了但线上跑的还是旧 bundle」。

**背景**


**根因**

无流程约定：Bug 修复完成后缺少默认的「复审 → 复部署」环节，执行结果与部署验证脱节。

**修复动作**

建立规则：Bug 修复后必须走 复审（CLO-192）→ 复部署（CLO-191）闭环，后续默认执行。

**验证结果**

CLO-187 修复完整走完 复审（CLO-192 done）→ 复部署（CLO-191 done）→ 验证通过，loop 规则在 CLO-159 内闭环验证。

**经验教训**

- Bug 修复的标准动作不是「修完即可」，而是「修复 → 复审 → 复部署 → 验证」四步闭环，任何一步缺失都是流程缺陷。
- 规则一旦确立应写进拆解模板/AGENTS，让后续特性自动带上复审 + 复部署阶段，而不是靠用户提醒。
- 问题 8（无人部署）本质是 loop 规则的执行断链，规则有了，执行保障（触发 + 超时兜底）也要跟上。
