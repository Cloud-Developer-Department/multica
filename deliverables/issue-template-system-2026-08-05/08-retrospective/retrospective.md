### 三.1 规划阶段问题

#### P1. 交付物只有路径、没有内容，用户无法预览

- **现象**：Research 完成调研后仅给出仓库路径，用户无法在 issue 页面预览 md 内容。
- **时间线**：08-04 03:50（交付）→ 03:51（用户反馈）→ 03:57/03:58（全文贴入评论）。
- **根因**：交付规范执行不到位 —— 只报了路径，未把内容同步到 issue 评论；后续又发现「贴内容」的格式也不对（应贴 md 附件文件便于渲染预览，而不是 content-file 纯文本）。
- **修复动作**：将两份调研报告全文贴入 issue 评论；并约定 md 以附件（`--attachment`）形式提供，可渲染预览。
- **验证结果**：用户可正常预览全部调研报告。
- **经验教训**：交付件三要素缺一不可 —— ①仓库落库；②issue 评论说明 + 关键内容；③md 以附件形式贴出便于渲染预览。

#### P2. 子任务交 `in_review` 导致 Stage 流水线断链（2 次）

- **现象**：前端（CLO-164）、审查（CLO-162）完成后任务停在 `in_review`，Stage 屏障不关闭，后续 Stage 不自动推进，用户连续两次问「又不动了 / 为啥不是 done」。
- **时间线**：08-04 07:08（CLO-164 完成未置 done）→ 07:10 用户反馈 → 07:11 手动纠正；08:03（CLO-162 同问题）→ 08:06 纠正。
- **根因**：**Stage 屏障只认 `done`/`cancelled` 为终态，`in_review` 不产生 Stage 完成事件**。执行 Agent 沿用通用「交活即 in_review」的默认习惯，未按流水线约定置 `done`。
- **修复动作**：Orchestrator 手动置 `done` 恢复推进；并在后续拆解时明确「完成后置 `done`，审查交给独立 Stage 的 Review 角色」。
- **验证结果**：纠正后 Stage 事件正常触发，流水线恢复。
- **经验教训**：流水线内角色（Coding/Validation/Documentation 等）完成任务必须置 `done`，`in_review` 只留给独立审查 Stage；拆解描述里应显式写明终态约定，避免 Agent 默认行为断链。

#### P3. 小队缺少独立架构师角色

- **现象**：用户指出当前小队无架构师，Research 与 Architect 定位不正交。
- **时间线**：08-04 03:58 记录。
- **根因**：squad 角色设计为 7 个固定角色（Orchestrator/Research/Coding/Validation/Review/Documentation/DevOps），未包含独立 Architect；架构设计职责被 Research 兼任。
- **修复动作**：记录为 squad 结构层面的改进项，本次特性继续推进，未阻塞。
- **验证结果**：作为长期整改项登记，不在本 issue 内解决。
- **经验教训**：研究与架构设计是两种职责（调研事实 vs 设计方案），建议在 squad 角色模型上拆成正交角色；至少在复杂特性的拆解阶段显式指定架构设计责任人。

#### P4. 执行角色完成任务后未 @ 用户复核

- **现象**：Research、Coding 完成交付后没有 @ 用户请求复核。
- **时间线**：08-04 03:58（用户指出）→ 05:53（用户明确：后续无须 @ 我，Orchestrator 把控节奏）。
- **根因**：Leader 复核流程没有在角色交付时强制要求 @ 用户。
- **修复动作**：先要求执行角色完成时 @ 用户；随后用户改为「无需 @ 我，Orchestrator 统一把控节奏」——复核责任收归 Leader。
- **验证结果**：后续节奏由 Orchestrator 统一推进，用户不再逐点介入。
- **经验教训**：复核流（谁复核、何时复核、怎么通知）要在拆解时就定死；对 Owner 明确「节奏由 Leader 把控」后，各角色应统一向 Leader 汇报而非打扰用户。

#### P5. 子任务漏排「部署」环节，DevOps 无事可做

- **现象**：最初拆解只有 6 个 Stage，无部署；用户质问「yaoming 干啥？不要讲现象，说理由」。
- **时间线**：08-04 07:33 用户指出 → 07:33 补建 CLO-169（Stage 7）。
- **根因**：拆解时参照了 Agent 模板系统（该功能未走独立部署流程）的既有模式，导致部署被漏排；同时用户口头补充的「本地部署」要求未同步进子任务管线。
- **修复动作**：新增 CLO-169（本地部署），分配 DevOps，排在 Stage 7；并承诺后续拆解完整覆盖 DevOps 部署环节。
- **验证结果**：CLO-169 正常执行并产出部署报告/指南/回滚方案。
- **经验教训**：拆解清单应固定模板化检查 —— 调研/研发/测试/审查/文档/**部署**/复盘缺一不可；Owner 的口头补充要求必须立刻落进子任务管线，不能只停留在评论确认。

- **修复动作**：DevOps 收拢 —— 将单链提交（后端→前端→测试→文档→部署→Bug 修复）统一到 `Equipment_Department_Exploration`，提交统一 PR #2（90 文件，+4020/-65）；删除远端 6 个散落分支；PR #3 补入此前未入库的 Bug 修复交付件。
- **验证结果**：PR #2 已合并、分支清理完成、交付物完整（删除前均校验为特性分支祖先或空基线，无内容丢失）。
- **经验教训**：拆解阶段就要约定共享特性分支（如 `feature/<特性名>`），所有角色基于同一分支工作或 PR 合入，避免每步自动建分支造成的仓库散落与收拢成本。DevOps 收拢时「单链提交、无冲突」是本次收拢成本低的客观原因，不能指望每次都如此幸运。

### 三.3 功能 Bug（部署后用户实测）

#### P7. issue 展示不全 + 无法使用模板创建（CLO-172）

- **现象**：本地部署后用户实测：Settings 模板页无预置模板、「从模板创建」下拉不渲染。
- **时间线**：08-04 08:42 用户报告 → 08:43 建 CLO-172 → 09:46 修复完成。
- **根因**：后端 `parseLabelIDsJSONB` 对空标签数组返回 Go `nil` → JSON 序列化为 `null`；前端 zod schema `z.array().optional().default([])` 对 `null` 校验失败（default 只对 `undefined` 生效），`parseWithFallback` 回退空列表 → 前端拿到 0 个模板。
- **修复动作**：后端 `parseLabelIDsJSONB` 所有空/无效路径返回 `[]string{}`（JSON 输出 `[]`）；前端 schema 改 `.nullish().transform(v => v ?? [])` 兼容 `null`。改动 2 文件 7 行。
- **验证结果**：本地全链路通过（`GET /api/issue-templates` 返回 4 个预置模板、`label_ids=[]`），typecheck 6/6、core 1066 测试全过。
- **经验教训**：前后端联调不完整是主因 —— 后端序列化语义（`nil` vs `[]`）与前端 schema 容错必须作为联调验收项；**预置数据（含空数组字段）必须在真实链路里端到端验证**，不能只测「正常数据」路径。Go 端「空值返回 nil 还是空切片」应作为代码规范固化。

#### P8. 模板正文内容在新建 issue 时未带出（CLO-187）

- **现象**：选择模板创建 Issue，标题/优先级等带出，但正文（description）不填充。
- **时间线**：08-05 01:40 用户报告 → 01:41 建 CLO-187 → 01:54 修复 → 02:19 复审通过 → 02:43 复部署验证通过。
- **根因**：`applyTemplate` 应用模板时通过 `setFormResetKey` 递增 key 重挂载编辑器以读取新 `defaultValue`，但只有 `TitleEditor` 挂了 `key={formResetKey}`，`ContentEditor` 没有；而 `ContentEditor` 的 `defaultValue` 是 mount-only（仅挂载时读取）。
- **修复动作**：`packages/views/modals/create-issue.tsx:882` 为 `ContentEditor` 补上 `key={formResetKey}`（与 `TitleEditor:867` 一致）+ 新增回归测试。
- **验证结果**：回归测试修复前失败、修复后通过；create-issue 套件 37/37、quick-create 17/17；复部署端到端验证通过（Playwright 真实浏览器确认正文带出）。
- **经验教训**：重挂载驱动 defaultValue 是 React 常见陷阱 —— 只要「用 key 重挂载来刷新编辑器值」，就必须给所有相关编辑器统一挂 key，前后端语义对齐要一致；修复必须配回归测试，且修完走完整闭环（见 P4a/P4b）。

### 三.4 流程执行问题

#### P4a. Bug 修复后缺少固定 loop（复审 → 复部署）

- **现象**：第一次 Bug（P7）修复后只走了 Coding 自验证，未建立「修复 → 复审 → 复部署」的固定闭环；用户明确记录「修改 bug 后，要有 loop 的动作，再一次 review、部署等等动作」。
- **时间线**：08-05 02:08 用户记录 → 建 CLO-192（复审）+ CLO-191（复部署）。
- **根因**：无流程约定，Bug 修复被视为 Coding 单点完成，没有把 Review/Deployment 强制纳入修复后的必须环节。
- **修复动作**：建立规则 —— **Bug 修复后默认执行完整 loop：Coding 修复 → Review 复审 → DevOps 复部署**；每条 Bug 修复任务拆成修复 + 复审 + 复部署三类子任务。
- **验证结果**：CLO-187 走通该 loop（修复 → 复审 Approve → 复部署通过），成为后续所有 Bug 修复的默认流程。
- **经验教训**：Bug 修复 ≠ 改完代码，必须含「修复 → 复审 → 复部署 → 回归验证」闭环，否则修复质量与可交付性无保证。该规则应写进小队流程规范。

#### P4b. Bug 修复后无人部署（CLO-191 停摆）

- **现象**：用户记录「修改 bug 后，没人部署」——CLO-191（复部署）置 todo 后长时间无执行记录。
- **时间线**：08-05 02:22-02:23 CLO-191 置 todo → 02:31 用户反馈 → 02:32 Orchestrator 直接触发 DevOps → 02:43 复部署完成。
- **根因**：任务虽置 todo，但未形成有效的执行保障（无唤醒、无人认领、无兜底检查），Orchestrator 也未及时发现任务停摆。
- **修复动作**：Orchestrator 直接向 DevOps 触发复部署，并基于已合并的 PR #4 代码执行；对 todo 任务增加停摆监控/兜底。
- **验证结果**：复部署完成且验证通过，Bug 修复 loop 闭环。
- **经验教训**：任务置 todo 不等于会被执行 —— 需要「认领 + 心跳 + 兜底」三重保障；Leader 要主动巡检停在 todo/in_progress 的任务，不能让「等通知」成为断链点。

## 五、改进措施与后续整改

1. **拆解模板化**：每个特性拆解强制检查「调研/研发/测试/审查/文档/部署/复盘」全环节，禁止参照历史不完整流程导致漏项。
2. **终态约定写入子任务描述**：流水线内角色完成后置 `done`；`in_review` 只用于独立审查 Stage。防止 Stage 屏障断链。
3. **分支治理前置**：拆解时即约定共享特性分支（`feature/<特性名>`），角色提交经 PR 合入；DevOps 巡检散落分支。
4. **Bug 修复闭环化**：任何 Bug 修复默认拆为「修复 + 复审 + 复部署」三段，缺一不可。
5. **任务停摆兜底**：Leader 定期巡检 todo/in_progress 子任务，认领 + 心跳 + 兜底三重保障，避免「等通知」断链。
6. **前后端契约校验**：序列化语义（`nil` vs `[]`、`undefined` vs `null`）纳入联调验收清单；预置/空值路径端到端验证。
7. **squad 角色模型**（长期）：评估引入独立 Architect 角色，使 Research（事实调研）与 Architect（设计决策）正交。
