## 2. 表结构可用字段速查（v2.0 新增 VCS/身份相关）

### 2.1 VCS 集成表（迁移 216–221）——**本平台 Git 模块可复用的关键底座**

`vcs_connection(workspace_id, provider('forgejo'|'gitea'|'gitlab'), instance_url, access_token_encrypted, webhook_secret_encrypted, created_at, updated_at)`
`vcs_pull_request(workspace_id, connection_id, provider, repo_owner, repo_name, pr_number, title, state('open'|'closed'|'merged'|'draft'), html_url, branch, head_sha, author_login, merged_at, closed_at, pr_created_at, pr_updated_at, additions, deletions, changed_files)`
`issue_vcs_pull_request(issue_id, pull_request_id, close_intent, reference_only, linked_by_type, linked_by_id, linked_at)`
`vcs_commit_status(connection_id, sha, context, state, target_url, description, updated_at)`

> ✅ 平台已实现 **token 型 Git 平台接入**（Forgejo/Gitea/GitLab），含 PR 镜像（新增/合并/关闭 Webhook）、Issue↔PR 关联、CI 状态镜像。**GitCode 为自托管 Git 平台，可按 Gitea/Forgejo 兼容协议接入**，或经本地仓库分析口径先行（§7）。
> ⚠️ 现有 Provider 枚举仅含 forgejo/gitea/gitlab；接入 GitCode 需在 `server/internal/integrations/vcs` 注册 GitCode provider 或确认其兼容 Gitea 协议（待 Leader + 研发确认）。

### 2.2 GitHub 集成表（迁移 079/127/222）

`github_installation`、`github_pull_request`（同 vcs_pull_request 结构 + `api_mergeable` 等快照字段）、`issue_pull_request`、`github_pull_request_check_run`。

> ✅ 平台同时支持 GitHub App 集成。若团队实际代码托管在 GitHub，可直接用此链路支撑 Merged/PR 口径。

### 2.3 身份/部门相关表现状

`user(id, name, email, avatar_url, onboarded_at, created_at, updated_at)`；`member(id, workspace_id, user_id, role('owner'|'admin'|'member'), created_at)`

> ❌ **本地库无 LDAP/IDP 集成、无部门字段、无离职/熔断事件日志**。用户生命周期、部门维度、权限熔断成功率均需外部数据或手动维护（§9）。`user.onboarded_at` 可支撑「开通账号时间」但**不能**用于推导「入职总人数」（会把存量用户/Agent 误判为入职，见《数据口径》§1.4.1）。

### 2.4 部署/流水线相关表现状

> ❌ **本地库无部署流水线表、无部署事件表、无 CI/CD 关联**。DORA 四项指标全部依赖外部部署数据接入（§8）。

### 2.5 本地仓库数据现状核对（Git 侧落地口径）

- `workspace.repos`（JSONB，迁移 014）保存工作区配置的仓库列表。
- 本地部署为 Git 仓库（`C:\multica-deploy\multica`，分支 `Equipment_Department_Exploration`），仓库内已有提交历史（`git log` 可用）。
- 团队其他仓库（clubdeveloperclub / wish-wall / team-engineering-governance / practicecenter / kj-skills / agent-lessons）均为本地 Git 仓库。

> ✅ 本地仓库分析口径可落地：对 `workspace.repos` 指向的本地路径执行 `git log --numstat` 等命令，可统计提交数、作者、增删行（ELOC 兜底行数）、按天活跃。

## 4. 明确标注的数据缺口（一期，v1.0 保留）

1. **Merged（漏斗第三段）**：一期返回 `null`；二期接入 VCS 后实现（表已具备）。
2. **技能真实调用次数**：一期代理口径；真实调用级需研发补 `task_skill_usage` 表（二期增强）。

5. 部门维度 / LDAP / 部署流水线 / GitCode：v2.0 已给出接入方案（§7–§9），不阻塞一期。

## 7. GitCode 数据接入方案（2.3 Git 贡献，二期）

### 7.1 目标数据与现状缺口

| 数据 | 目标口径 | 现状 |
| --- | --- | --- |
| 提交数据（作者/时间/增删行） | ELOC、活跃度、提交数 | 本地仓库 `git log` 可算；线上提交需 GitCode 接入 |
| PR 数据（创建/合并/关闭） | PR 积压、合并周期 MTTM、活跃度 | `vcs_pull_request` 表可镜像；当前无线上授权/Webhook |
| 质量数据（覆盖率/漏洞/重复率） | 提交质量雷达 | 需外部扫描工具/CI 报告 |

### 7.2 接入方案（分级，可组合）

**方案 A：本地仓库分析口径（当前即可落地，无依赖）**
- 对 `workspace.repos` 中的本地仓库路径执行 Git 命令（`git log --numstat --since --until --pretty=format`）统计提交数、作者、增删行、按日提交数。
- ELOC 兜底：Cloc/SCC 输出**物理行数**，作为 ELOC 的 v0 口径（AST 当量见 7.3）。
- 优点：零依赖、今天就能出数；缺点：无线上 PR（PR 积压/合并周期需 7.2-B 或手动导入）。

**方案 B：VCS 连接接入（复用现有 vcs_connection 底座）**
- 平台已实现 token 型 Git 平台接入 + Webhook（迁移 216–221，`/api/webhooks/vcs/{connectionId}`）。
- 落地步骤：① 注册 GitCode provider（若其兼容 Gitea API/Webhook 协议，可直接复用 `gitea` provider，仅需 Leader/研发确认）；② 在 GitCode 实例创建账号 Token + 配置 Webhook；③ 通过现有 `ConnectVCS` 接口接入，PR/合并/CI 事件自动镜像入库。
- 支撑：PR 积压（`state='open'`）、合并周期（`merged_at - pr_created_at`）、活跃度（提交+PR）、Merged 漏斗段。
- 阻塞项：GitCode 线上实例的可用性与授权（当前需求基线注明「仅本地部署，无线上授权/Webhook」）→ 需 Leader 确认是否申请线上接入，**不阻塞方案 A 先行**。

**方案 C：文件导入（兜底）**
- 提供 PR/提交 CSV/JSON 导入接口，由运维手工导出 GitCode 数据导入。用于线上 Webhook 未开通时的过渡。

### 7.3 ELOC 工具链选型（待 Leader 拍板）

| 方案 | 说明 | 成本/复杂度 | 建议 |
| --- | --- | --- | --- |
| 行数兜底（Cloc/SCC） | 物理行数作为 v0 ELOC | 低 | 二期先行 |
| AST 当量工具（如 lizard + 各语言 AST 计数） | 真 AST 当量，剔除注释/空行 | 中 | 与行数并行出，Leader 确认口径后定版 |
| 商业工具（SonarQube LOC 等） | 与质量扫描同源 | 中高 | 若团队已有 SonarQube 可顺带启用 |

> 需求基线 CLO-227 已「接受引入 AST 代码当量工具链」。推荐二期先以 Cloc/SCC 行数兜底上线，同时评估 AST 工具，口径稳定后切换，避免依赖空转。

### 7.4 提交质量雷达数据接入（外部扫描）

| 轴 | 接入方式 | 优先级 |
| --- | --- | --- |
| 测试覆盖率 | CI 覆盖率报告导入（JaCoCo/istanbul 等）或扫描工具输出 | 中 |
| 静态扫描漏洞 | SonarQube/Semgrep 结果导入（`repo_quality_snapshot` 表） | 中 |
| 代码重复率 | SonarQube/PMD-CPD 结果导入 | 中 |

- 新表建议：`repo_quality_snapshot(repo, coverage, vulnerabilities, duplication_rate, snapshot_at, created_at)`，由导入任务写入。
- 未配置 → `source_status.ready=false`，页面引导态。

## 8. 部署流水线数据接入方案（2.4 DORA，三期）

### 8.1 现状

本地库无任何部署/流水线表。DORA 四项指标（交付周期/部署频率/变更失败率/MTTR）必须外部接入。

### 8.2 接入方案（可组合，按优先级）

**方案 A：部署事件 Webhook / 接口上报（推荐）**
- 新增部署事件上报接口 `POST /api/analytics/dora/deployments/events`（鉴权：工作区 Token）。
- 部署流水线（Jenkins/GitLab CI/自定义脚本）在部署成功/失败时回调，写入 `deployment_event` 表（字段见《数据口径》§4.0）。
- 支撑全部四项 DORA 指标。需研发在部署流程加一行 curl/回调。

**方案 B：文件导入**
- CSV/JSON 导入接口，运维定期导出部署记录导入（`deployment_event` 表）。

**方案 C：手动配置**
- 无自动化流水线时，由运维在平台手动录入部署记录（表单或批量导入）。

### 8.3 替代口径（部署未接入时）

- **交付周期降级为「Issue→Merged」**（PRD §4.4.1）：二期接入 VCS 后即可先行展示；部署接入后切回「Issue→部署」并保留切换开关。
- **部署频率/变更失败率/MTTR**：无部署数据 → `null` / `[]`，页面引导态，**不得用 Issue 状态造数**（口径发明风险）。

### 8.4 阻塞项

- 需要团队部署流水线（或手动运维流程）配合上报/导入部署事件 → 需 Leader 确认团队现有部署方式，安排接入任务。

## 9. LDAP/IDP 数据接入方案（2.1 身份与部门，三期）

### 9.1 现状

本地库无 LDAP/IDP 集成、无部门字段、无离职/熔断日志。

### 9.2 接入方案

**方案 A：LDAP/IDP 目录同步（推荐，需 LDAP 实例）**
- 通过 LDAP/SCIM 同步用户状态（在职/离职）、部门归属到 `user`/`member`。
- 部门字段：`member.department`（TEXT，外部部门 ID）。
- 离职熔断：LDAP 离职事件触发平台权限回收（禁用账号/移除成员/吊销 Token）并落 `activity_log` 日志（新 action：`member_disabled`/`member_removed`/`token_revoked`）。
- 入职开通率：以 LDAP 入职事件为分母，`user.onboarded_at` 为开通依据。
- 阻塞项：需要企业 LDAP/IDP 实例与凭据 → 需 Leader 确认是否提供。

**方案 B：手动维护（可先行）**
- 管理入口：维护成员→部门映射（`member.department`）+ 入职/离职事件（`identity_import` 表）。
- 支撑：部门维度切片（L2 + 各接口 `department_id`）、生命周期卡（手动事件）、权限熔断成功率（手动记录）。
- 优点：不依赖 LDAP 即可点亮 Tab1 ⑥⑦⑧ 与部门筛选器；数据由管理员手工维护。

### 9.3 替代口径与不可行项

- 入职开通率：无 LDAP 入职总人数时 `null`（引导态），**不得用 `member.created_at` 造入职**。
- 离职权限熔断：无外部事件时 `0` + 引导态；手动模式可录入。
- 权限熔断成功率：手动模式需记录应熔断/成功数；LDAP 接入后自动。

### 9.4 阻塞项

- 若团队既无 LDAP 实例又不接受手动维护，则生命周期/部门维度模块以引导态呈现（`source_status.ready=false`），功能不阻塞其他看板。
